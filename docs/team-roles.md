# 团队角色与协作约定（实验三 步骤 1）

> 本文件记录角色、职责和协作规则；成员姓名、学号以《实验三 实验报告》成员表为准。仓库内按角色标识，避免把个人信息写进公开仓库。

## 团队与角色

| 角色 | 人数 | 主要职责 |
|---|---|---|
| 产品负责人（PO） | 1 | 维护 Sprint Backlog、解释需求、验收用户故事、审批变更是否进入当前迭代 |
| Scrum Master（SM） | 1 | 主持每日站会、控制 5 分钟时间盒、维护看板与障碍清单、组织回顾 |
| 配置管理员（SM 兼） | 1 | 配置项识别、版本号与标签管理、变更控制记录、发布检查 |
| 开发成员 | 2 | 功能开发、测试补充、代码评审、缺陷修复 |

## 协作约定

- **站会**：每个工作日 09:30，时长 ≤ 5 分钟；每人回答三问（昨天完成、今天计划、是否有障碍），每人发言 ≤ 2 分钟。
- **站会边界**：只同步进度和暴露障碍，不做技术方案讨论；需要深入讨论的问题由 SM 在站会后 30 分钟内组织专题小会。
- **看板**：任务状态统一为“待办 / 进行中 / 已完成 / 阻塞”，站会后立即更新。
- **分支策略**：简化的 GitHub Flow；`main` 始终保持可发布，功能从 `main` 拉 `feature/*`，缺陷用 `bugfix/*`，线上紧急修复用 `hotfix/*`。
- **合并规则**：不直接向 `main` 提交；所有变更通过 Pull Request；至少 1 名其他成员 Code Review 通过后合并；合并后删除功能分支。
- **提交规范**：Conventional Commits，例如 `feat:`、`fix:`、`test:`、`docs:`、`chore:`、`refactor:`、`merge:`。
- **版本发布**：语义化版本 `MAJOR.MINOR.PATCH`；可发布版本由 SM 打 annotated tag，并同步 Release Notes。
- **质量门禁**：PR 必须通过 Ruff、Bandit、pytest 覆盖率门槛；核心模块 ≥ 80%，增量代码 ≥ 60%。

## 本 Sprint 的质量目标

| 目标 | 度量 |
|---|---|
| 核心流程可演示 | US01–US05、US08 验收清单通过 |
| 自动化回归 | pytest 全绿，核心覆盖率 ≥ 80% |
| 静态扫描 | 0 Blocker/Critical，Major ≤ 5，重复率 ≤ 3%，CC ≤ 10 |
| 评审闭环 | ≥ 3 条具体意见闭环，至少 1 人 approve |
| 缺陷响应 | 按时响应率 ≥ 90% |
